# v3 → v4 gap analysis

Recorded 2026-08-01, against HEAD `2f3466a`. Companion to `docs/spec-v4.md`.

**Nothing described here has been implemented.** This is a survey of what the
repository currently does, what v4 requires, and what stands between them. No
code, config, arm definition, or test was changed in writing it.

---

## 1. Where the repo stands

The tree is clean and matches `origin/main`. 60 tracked files. Both suites
pass: **212 passed / 15 skipped** in `.venv` (no torch), **227 passed** in
`.venv-ml`. The skips are the optional-dependency tests and are the deliberate
evidence that `burst/` needs no ML stack.

Everything in `burst/`, `configs/`, `scripts/`, and `tests/` implements v3.

## 2. What v4 breaks, file by file

### `burst/config.py`

- `ARMS` at line 62 is `("coherent", "noise", "ordinary", "twin")`. Wrong three
  ways under v4: `ordinary` is deleted, `noise` is renamed `scrambled`, and two
  arms are missing.
- `INJECTING_ARMS` at line 67 has 3 members; v4 has 5.
- `BurstTextPaths` is a frozen dataclass with exactly three fields and a
  `for_arm()` written as an explicit if-chain. Every arm needs a field and a
  branch.
- `_validate_semantics()` raises if `tuple(cfg.experiment.arms) != ARMS`, so
  the YAML and the code constant must move together.
- `Config.checkpoint_plan.estimated_bytes_all_runs` multiplies by
  `n_seeds × len(arms)`. At 6 arms the study-wide storage estimate rises 50%,
  and the TB figure the CLI prints is currently understated by that much.

### `configs/`

- `experiment.arms` lists the four v3 arms.
- `injection.injection_step` is `null`. **v4 fixes it at 200.**
- `injection.burst_length_tokens` is still `null` and still undecided.
- `injection.burst_text_paths` has three keys, all `null`. **Nothing in
  `configs/` points at `bursts/` and nothing in `bursts/` reads the config.**
- `configs/runs/` holds 40 generated override files. v4 needs 60. They are
  generated by `scripts/generate_overrides.py` from `n_seeds` and `arms`, so
  the count follows the arm list automatically — but 20 new files appear.

### `scripts/make_bursts.py`

Written around exactly two generated outputs, in a dozen places. This is a
shape to change, not a parameter.

- `COHERENT_NAME`, `ORDINARY_NAME`, `NOISE_NAME` are three separate string
  constants (lines 65–67). These want to become one arm registry mapping arm →
  (filename, generator, hand-written?).
- `_run()` declares two named output paths, unpacks `select_spans(docs, 2, …)`
  into two variables, calls `trim_to_tokens` twice, `write_text` twice, builds
  the count dict from a hardcoded 3-tuple, and writes `provenance["files"]` as
  three literal blocks.
- `select_spans()` takes `n_spans` as a parameter but is **called with the
  literal `2`** at `make_bursts.py:541` and `match_sweep.py:210`.
- The write guard compares outputs against a single `coherent_path`. With two
  hand-written arms it must check a set.
- `--k` is required unconditionally. With one of five arms using a window
  shuffle, that becomes wrong.
- `SPAN_WORD_MULTIPLIER = 2.0` is global and calibrated for English. It must
  become per-arm; see §5.
- Two new generators needed (POS-substituted, random-characters), and
  fluent-true cannot be generated at all.

### `bursts/`

- `ordinary.txt` is no longer an arm. It is not useless — it is the kind of
  substrate scrambled and POS-substituted are cut from — but its role changes
  from output to input.
- `noise.txt` is misnamed under v4 vocabulary.
- `provenance.json` carries `window_size_k` as a **top-level** field. With only
  one arm using a window shuffle, arm-specific parameters must move inside each
  file's entry. The `files` dict is otherwise already the right shape.
- A `pos_vocabulary_hash` or equivalent is needed or the POS arm is not
  reproducible — the substitution vocabulary determines that arm's loss.

### `scripts/burst_match.py`

- `Measurement` is a frozen dataclass with 8 fields and no place for a gradient
  vector. Cosine similarity needs the vectors, not the norm.
- `gradient_norm(loss, model)` consumes the gradients and returns a float,
  discarding them. It wants splitting: one function returning the per-parameter
  gradient tuple, thin functions computing norm, cosine, and anisotropy from
  it. The float64 accumulation and fixed parameter ordering must survive —
  ordering becomes *load-bearing* for cosine similarity in a way it is not
  today, since two gradients must flatten identically.
- Memory: a flattened fp32 gradient for GPT-2 is **~498 MB**. Five arms held
  simultaneously is ~2.5 GB. Hold / stream pairwise / project to a random
  subspace is an undecided design question.
- `format_comparison()` builds a table at 78-character width. A five-arm
  pairwise cosine matrix is 10 pairs and will not fit. That table needs
  redesign, not extension.
- **No results persistence anywhere.** A cosine matrix and per-arm anisotropy
  statistics are not something to read off a terminal.

### `scripts/match_sweep.py`

Its whole shape is stale: one reference row, one row for a deleted arm, and N
rows sweeping k for one arm. Under v4, k is one arm's private parameter among
five. It has **zero test coverage**.

### `tests/`

- `test_config.py::test_burst_text_paths_start_null_in_the_real_base_config`
  asserts `set(paths) == {"coherent", "noise", "ordinary"}`. Fails on the arm
  rename alone, before any null-ness question.
- `test_all_forty_override_files_exist_and_are_two_lines` and
  `test_the_forty_runs_differ_only_in_seed_and_arm` hardcode forty.
- `test_make_bursts.py` has three tests iterating a hardcoded 3-tuple of
  filenames.
- Two `@pytest.mark.parametrize("arm", ARMS)` tests expand automatically.

### New dependencies for POS substitution

None installed. spaCy (plus an ~12 MB model, and it pins numpy tightly against
the installed `numpy==2.5.1`), NLTK (plus `averaged_perceptron_tagger` and
`wordnet` corpora, which download at runtime to a path `.gitignore` does not
cover), or a heavier torch-based tagger. Each adds a `measure`-group pin, a new
cache directory, and a new offline-availability failure mode.

## 3. The matching target — three options, none chosen

`burst_match.py` measures a bare 194-token sequence with no context. At
injection the burst sits inside one 1024-token sequence inside a 256×1024
batch, and the applied gradient is the batch gradient.

**A scaling note that cuts across all three.** `batch_scaled()` divides the
standalone gradient norm by `batch_size` (256). That is exactly right *if the
burst constitutes an entire sequence* and the batch loss is the mean of
per-sequence mean losses. If the burst is 194 tokens inside a 1024-token
sequence and the batch loss is a token-level mean over all 262,144 predictions,
the burst tokens carry weight 194/262,144 ≈ **1/1351** — making the printed
figure **~5.3× too large**. Which is correct depends on a loss-reduction
convention nothing in the repo states.

### Option A — burst alone (status quo)

*To measure:* nothing; `measure_text()` does this today.
*Cost:* one forward + backward over 194 tokens. Seconds on CPU.
*Collected numbers:* they **are** this quantity and stay valid.
*Does not capture:* the burst's first token is predicted from nothing. In the
2026-07-31 run the single highest-loss token in the fluent-false passage was at
**position 1** — essentially the unigram prior, a pure artifact of isolation.
It inflates every arm's mean, and unequally: how much an opening benefits from
prior context depends on how predictable it is, which is exactly what differs
between fluent-false and random-characters.

### Option B — burst inside a 1024-token sequence

*To measure:* three undecided conventions, each a confound if chosen carelessly.
**Position** (front/middle/end — sets left-context and downstream reach; must be
identical across arms). **Filler** (the other ~830 tokens; must be
byte-identical across arms, making it a committed sixth artifact with its own
provenance). **Loss scope** — burst tokens only keeps arms comparable but makes
the reported loss and the differentiated objective different things; all 1023
makes them consistent but dilutes between-arm signal roughly 5× toward the
tolerance floor.
*Cost:* ~5× option A. Still seconds. The expense is design surface.
*Collected numbers:* invalidated. Losses fall as burst tokens gain context, by
different amounts per arm. The filler gradient adds **vectorially**, so old
numbers cannot be rescaled into new ones.

### Option C — full-batch delta

∇L(batch with burst) − ∇L(batch with burst replaced), the actually-applied
contribution.
*To measure:* 255 other real corpus sequences per batch — i.e. the data
pipeline, which does not exist. Two full-batch backward passes per arm.
*Cost:* 262,144 tokens per pass, ~1350× option A, twice per arm. **Not
CPU-feasible**; only `torch==2.13.0+cpu` is installed. Two ~498 MB gradient
vectors held simultaneously to difference them, plus batch activations.
*Collected numbers:* not comparable. Would settle the 1/256-vs-1/1351 question
empirically.

### The cross-cutting risk

Arms matched under A are not thereby matched under B or C. Matching is a
property of the measured quantity, not of the passages. Match on A and inject
under C and the arms could be matched on the measured thing and unmatched on
the applied thing, with nothing currently planned to detect it.

## 4. The rng discrepancy — unresolved

`make_bursts._run()` threads **one** generator through both operations:

```python
rng = random.Random(args.seed)
ordinary_span, noise_span = select_spans(docs, 2, span_words, rng)
shuffled = window_shuffle(noise_span.text, args.k, rng)
```

`select_spans()` calls `rng.shuffle(candidates)`, consuming draws that depend on
`len(candidates)` — itself a function of `--docs`, `SPAN_WORD_MULTIPLIER`, and
document lengths. The shuffle then continues from that advanced state.

`match_sweep._run()` uses **two** generators and re-creates the second per k:

```python
selection_rng = random.Random(args.seed)
_, noise_span = select_spans(docs, 2, span_words, selection_rng)
shuffled = window_shuffle(noise_span.text, window, random.Random(args.seed))
```

Both select the same span; they diverge at the shuffle. Confirmed empirically —
see `docs/measurements/2026-07-31-match-sweep.md`.

**Affected:** `bursts/noise.txt` (is the threaded-rng output);
`bursts/provenance.json` (its recorded sha256 matches the file — internally
consistent, but describes a text the sweep never measured); the sweep's noise
rows (describe texts that exist nowhere). **Unaffected:** `ordinary.txt` (never
shuffled), `coherent.txt` (never generated).

`implementation-notes.md` S26 claims the sweep "measures the passage that
script would actually produce." **That sentence is false as written.**

### The two candidate conventions

**A — one stream per run.** A seed defines a single deterministic sequence
covering the whole generation. Changing `--docs` or `SPAN_WORD_MULTIPLIER`
changes the shuffle at identical seed and k. Under v4 the sharp edge: with five
arms generated in one run, **arm 5's text depends on how many draws arms 1–4
consumed**, so adding, removing, or reordering an arm silently changes the
content of arms generated after it.

**B — fresh stream per operation.** Each shuffle is `Random(seed)`, independent
of history; arms and rows are mutually independent and reordering perturbs
nothing. Cost: operations sharing a seed draw the same underlying sequence, so
shuffles across arms or k values are *correlated* rather than independent.

A third exists that neither uses: a per-purpose sub-seed,
`Random(hash((seed, arm, k)))` — independence under reordering plus
decorrelation. Named for completeness.

Either convention is defensible. One of each, in two scripts meant to describe
the same passage, is not.

## 5. Why five-way matching is harder than two-arm

### The knob count is the structural problem

Two-arm matching had one fixed target and one tunable arm with one knob.
Five-way matching on two quantities at fixed token length is eight equality
constraints. The knobs are not eight:

- **fluent-false** — given, fixed. Zero knobs. It is the reference.
- **fluent-true** — must be *written* to hit a loss and gradient-norm target.
  No mechanical knob; the instrument is an author rewriting prose.
- **scrambled** — one knob, k. See below.
- **POS-substituted** — the substitution vocabulary is the knob, and a good one
  (rarer substitutions raise loss). But it must be committed and hashed or the
  arm is not reproducible.
- **random-characters** — the character distribution is nominally a knob; see
  below for why it may not be an effective one.

**Two of five arms have no mechanical knob, and one of those two is the
reference.**

### k is already known to be a weak dial

From the 2026-07-31 sweep: loss climbs monotonically with k while gradient norm
sits in a 21.8–23.6 band across the whole range, minimum gap **+27.7%** from
coherent. If tolerance is tighter than ~28%, the scrambled arm cannot be
matched by tuning k with that source span at all. If one knob cannot satisfy
two constraints for the *easiest* generated arm, it is unlikely to for the
harder ones.

### Random characters and the 194-token target

Measured bytes-per-token in the committed artifacts: `coherent.txt` **4.96**,
`ordinary.txt` **4.90**, `noise.txt` **3.78**. The scrambled arm is already 24%
denser than fluent English — word-order shuffling alone breaks BPE merges and
multiplies space-prefixed variants. That is a preview of the extreme.

GPT-2's BPE is trained on English; random character sequences hit almost no
learned merges and fragment toward byte level, roughly **1 token per 1–2
characters**.

- **On N.** 194 tokens of random characters is roughly **200–400 characters**
  against 962 for fluent-false. At matched token length the arms differ 3–5× in
  physical text length. "Same length" is true in exactly one sense.
- **On `SPAN_WORD_MULTIPLIER = 2.0`.** Calibrated for English at ~0.8
  tokens/word. For random characters it is either meaningless (generated de
  novo) or wildly overshooting (388 corrupted words would yield well over 1,000
  tokens, all but 194 discarded). It must become per-arm, each value justified
  against that arm's own token density.
- **On `trim_to_tokens()`.** Its bounded 16-iteration decode/re-encode
  correction assumes BPE round-trips. Byte-level BPE round-trips *valid text*,
  but random characters spanning non-ASCII can decode into replacement
  characters that re-encode differently. It raises `MakeBurstsError` on failure,
  so this breaks **loudly, not silently** — but it will break, and the fix is a
  design decision (restrict the alphabet to ASCII? generate at token level?)
  rather than a bug fix.
- **On matchability.** Random characters will carry per-token loss far above
  every other arm — plausibly 8–11 nats against fluent-false's 3.52. High loss
  and high gradient norm move *together*, so there is no obvious trade-off
  knob. **It may be impossible to bring this arm within any reasonable
  tolerance of fluent-false on either quantity**, let alone both, without
  diluting it with real text — which changes what the arm means. This is the
  arm most likely to force a tolerance revision or a design revision, and it is
  worth confronting before implementation rather than after.

### Smaller compounding issues

- **N = 194 is inherited, not chosen** — a property of a passage written for
  v3, enforced by nothing, with `injection.burst_length_tokens` still null.
- **Matching becomes a search, not a check.** Current tooling sweeps one
  parameter for one arm and prints a table. Multi-dimensional search with no
  results persistence means every candidate evaluated is lost to scrollback.
- **Gradient clipping is undeclared** and would distort exactly the
  cosine/anisotropy measurements v4 adds.

## 6. Landmines that survive unchanged

1. **`bursts/noise.txt` ≠ the sweep's k=5 row.** §4 above. Fails silently —
   every count matches, every assertion passes.
2. **Nothing connects `bursts/` to `configs/`**, and a test *asserts* the
   paths are null, so wiring them makes that test fail.
3. **N = 194 is implicit.** An editor adding a trailing newline to
   `coherent.txt` silently makes N 195. The tests that would catch it are the
   three tokenizer-gated ones that **skip in `.venv`** — so it breaks green on
   the torch-free environment.
4. **`n_spans=2` is a literal** at two call sites despite being a parameter.
5. **`"device:  cpu"` is a hardcoded string** at `burst_match.py:580`, not a
   detected value.
6. **Provenance points into a gitignored cache** with no dataset revision and
   no cache checksum.
7. **No structured output anywhere.** The reason this directory exists.
8. **Checkpoint size constants are estimates**, never measured against a real
   file. Labelled as such in the source and CLI.
9. **Test counts are duplicated** across `README.md`, `implementation-notes.md`,
   and this file, and must be hand-updated together.
