# The A6000 at bf16: a digest, a step time, and a node that cannot run anything

**Date:** 2026-08-07. **Commit:** `39973eb`, clean tree. **Jobs:** 54950
(gpmoo-b2, failed), 54954 (gpmoo-b1, failed — my error), 54955 (gpmoo-b1,
clean). **Question:** can the study use the A6000 nodes, and is mixing card
models safe?

## The short answer

**No to mixing, and the A6000 pool is not worth moving to.** An A6000 produces
different bits from an A100, and it is **1.82x slower** at bf16 — so eight of
them beat four A100s by 10%, not by 2x.

## 1. §0.C, confirmed with a digest rather than an inference

Same seed, same 30 steps, same config, `seed00_twin`, bf16, `micro_batch` 8:

| card model | digest |
|---|---|
| A100 — all three of a1's SKUs, two processes (54727) | `7e1fb0b9…d1358d` |
| **RTX A6000 — three cards, two load conditions (54955)** | **`1953bab5…e609f01`** |

**Different.** `docs/handoff-pilot.md` §0.C says an arm and a twin on different
card models "are not a valid pair"; S94 measured the mechanism (95 kernels on
the A100X against 92 on the A6000, identical code). This is the consequence,
as a number. The rule is not conservative — it is load-bearing.

## 2. Two determinism results, one of which closes an open gate

All four A6000 legs returned one digest:

| leg | card | condition |
|---|---|---|
| T30 | 3 | alone among this job's legs |
| C_gpu0 | 3 | **same physical card**, 3-way concurrent |
| C_gpu1 | 6 | 3-way concurrent |
| C_gpu2 | 7 | 3-way concurrent |

- **Same card, two processes, different system load, through `scripts/train.py`
  at bf16** — T30 against C_gpu0.
- **Card-to-card within the A6000 model** — 3, 6 and 7 agree, so any A6000 on b1
  is interchangeable with any other.

**This closes the gate S95 named**, and checking it turned up a stale claim: the
handoff says *"what has still never been run is two-processes-same-seed-same-card
through `scripts/train.py` itself at bf16"*. Pre-flight **54727 already did that
on the A100** — legs `a1_a100x_run1` and `a2_a100x_run2`, both on gpu 2, both
`7e1fb0b9…d1358d` — in the same job the bullet cites for its other half.
Corrected in place.

## 3. Speed: the datasheet was right this time

Startup cancelled the sizing doc's way, `(wall_60 - wall_30) / 30`:

| | s/step | h/run (9,536 steps) |
|---|---|---|
| A100X, bf16 (pilot v2, 4-up) | 3.84 – 3.99 | 10.17 – 10.56 |
| **RTX A6000, bf16 (54955)** | **7.267** | **19.25** |

**1.82x slower**, against a datasheet bf16 ratio of ~2x (312 vs ~155 TFLOPS).
Worth recording because S94 established the opposite habit — datasheet peaks
mispredicted this workload twice, and it concluded throughput here "is not a
function of the number on the box." Across *card models at one dtype* the number
on the box was approximately right; the cases S94 got wrong were across *dtypes
on one card*. Both facts stand; neither generalises to the other.

Contention was not the cause: three concurrent legs took 228–230 s against 229 s
for the same leg alone, so this job's own concurrency cost ~0.4%. Five unrelated
jobs were live on the node throughout, so 7.267 s/step is if anything an upper
bound.

## 4. What the pools are actually worth

At 10.56 h/run on an A100 and 19.25 h/run on an A6000, for a 40-run study
(4 confirmatory arms x 10 seeds):

| pool | runs/hour | 40-run study |
|---|---|---|
| 4x A100 (a1, available now) | 0.379 | **4.4 days** |
| 8x A6000 (one healthy node) | 0.416 | 4.0 days |
| 16x A6000 (b1 + b2) | 0.831 | 2.0 days |

**Eight A6000s are worth 10% over four A100s.** Only the full sixteen — which
needs b2 repaired *and* b1 empty — is worth the move, and it would restart every
hardware question from zero.

## 5. gpmoo-b2 cannot run anything

```
gpmoo-a1  A100 80GB PCIe / A100-SXM4-80GB / A100X   560.35.05   ok
gpmoo-b1  RTX A6000                                 560.35.05   ok
gpmoo-b2  Failed to initialize NVML: Driver/library version mismatch
          NVML library version: 580.173
```

The kernel module and userspace disagree — a driver upgrade to 580.173 without
a reboot. All ten legs of job 54950 died at model construction with
`CUDA error 803: system has unsupported display driver / cuda driver
combination`.

**SLURM still reports the node `idle` with `gpu:rtx_a6000:8` and will accept
jobs it cannot run.** That is a live hazard for a 10-hour study run, not just
for a 20-minute pre-flight. `sinfo` saying `idle` is not evidence a node works.

## 6. My own failure, recorded because it is the recurring one

Job 54954 died OOM on every leg with another process holding 39.45 GiB. Cause:
the script set `CUDA_VISIBLE_DEVICES` to absolute indices `0,1,2` instead of the
cards SLURM allocated, and landed on cards other jobs held. SLURM gave us `3 6
7`.

The a1 pre-flight (54727) uses the same absolute indices and works **only
because it requests all 8 cards**, so absolute and allocated indices coincide.
That is a latent trap in a script that currently passes. `pilot-v2.sbatch`
parses `CUDA_VISIBLE_DEVICES` and is the pattern to copy.

## Recommendation

**Stay on gpmoo-a1's four A100s.** The A6000 pool does not pay for itself at one
node, b2 is down, and b1 is occupied. Nothing about the study design changes.

Worth doing anyway: ask an admin to reboot b2. Eight idle A6000s is the largest
free block on the cluster and it is free because it is broken.
