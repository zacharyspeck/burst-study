# Sizing a virtualised A100: parity, a rejected optimisation, and determinism

**Date: 2026-08-08.** Host `instance-6ltvgvpi-main`, Thunder Compute,
1x NVIDIA A100-SXM4-80GB, driver 610.43.02, CUDA UMD 13.3, 8 vCPU, 64 GB RAM,
100 GB overlay filesystem. `torch 2.13.0+cu130`, `transformers 5.14.1`,
Python 3.12.13.

**The GPU is network-attached.** There is no `/dev/nvidia*` device on this host,
`/etc/thunder/config.json` reports `"gpuType": "A100XL", "gpuCount": 1,
"uvm": false`, and host-to-device bandwidth measures 2.03 GiB/s where a local
PCIe link would give an order of magnitude more. This is the first hardware in
this repo that is not a directly-attached card, so nothing about the pilot's
results could be assumed to carry over. All three measurements below exist
because of that.

## 1. Step time: at parity with cluster A100X

Repo's own `model_seam.build_model` at `configs/base.yaml` shapes, the
committed `micro_batch: 8` x 32 accumulation, bf16 autocast, `foreach` AdamW,
`use_deterministic_algorithms(True)`, TF32 off, `CUBLAS_WORKSPACE_CONFIG=:4096:8`.

| | this host | pilot v2 (gpmoo-a1, A100X) |
| --- | --- | --- |
| s/step | **3.725** (3.720, 3.722, 3.733) | 3.84 -- 3.99 |
| projected h/run (9536 steps) | **9.87** | 10.17 -- 10.56 |
| peak allocated | 12.3 GiB | 15.8 GiB recorded |
| params built | 124,439,808 | 124,439,808 |

Warm-up loss 10.98 against `ln(50257) = 10.82`, i.e. a correctly initialised
model. The 12.3 vs 15.8 GiB gap is this harness reusing one batch tensor and
doing no shard I/O; it is not a claim that the real loop is lighter.

Peak bf16 matmul on this card, 8192^3, host-synchronised: **237 TFLOP/s**
(76% of the 312 TFLOP/s dense figure). An earlier reading of 23,145 TFLOP/s was
an artefact of timing without pulling a value back to the host -- recorded here
because it is a plausible way to fool yourself on a virtualised device, where
`torch.cuda.synchronize()` returning is not by itself evidence the work ran.

## 2. Packing runs onto one card: MEASURED, REJECTED

The obvious optimisation, and the arithmetic argues for it: 52 TFLOP/s
sustained against 237 available, 12.3 GiB used of 80.

| concurrent runs on the card | s/step, each | aggregate steps/s |
| --- | --- | --- |
| 1 | 3.735 | **0.268** |
| 2 | 8.611 / 9.054 | 0.227 (**-15%**) |
| 3 | 12.317 / 12.352 / 12.432 | 0.242 (**-10%**) |

Two runs each take 2.4x as long, not 2x. Aggregate throughput falls. The loop
is bound by kernel-launch and virtualisation-channel serialisation rather than
arithmetic, and co-tenants queue behind each other on the one channel.

**Run one process per card.** The 22%-of-peak utilisation figure is not a
headroom figure on this hardware.

## 3. Determinism: holds, including under a co-tenant

```
CUBLAS_WORKSPACE_CONFIG=:4096:8 .venv-ml/bin/python probes/determinism/check.py \
    --model hf --steps 20 --dtype bf16
```

| condition | digest |
| --- | --- |
| card otherwise idle | `28f3ea04985094d46b3384064c62cd9af7bfca37e7c3467821dea3f30dc0b7b1` |
| unrelated training process on the same card | `28f3ea04985094d46b3384064c62cd9af7bfca37e7c3467821dea3f30dc0b7b1` |

Not merely `A == B` inside each run -- **the same digest across both
conditions**. A neighbouring process does not perturb a bit. This is what makes
eight concurrent single-GPU runs on one host safe; it says nothing about two
different hosts, which remains the untested case and the one the "same card
model" rule in `docs/handoff-pilot.md` §0.C is about.

### All eight cards agree, and so does the second box

**Measured 2026-08-08 after the resize to 8x A100.** The earlier result was one
card on each of two boxes, which establishes box-to-box equivalence and says
nothing about card-to-card equivalence *within* a box -- a gap the second box's
operator flagged, correctly, since runs are spread across all eight. The probe
inherits `CUDA_VISIBLE_DEVICES` rather than setting it, so it can be pinned:

```bash
for g in 0 1 2 3 4 5 6 7; do
  ( CUDA_VISIBLE_DEVICES=$g CUBLAS_WORKSPACE_CONFIG=:4096:8 \
    .venv-ml/bin/python probes/determinism/check.py --model hf --steps 20 \
      --dtype bf16 --outdir-root /home/ubuntu/probe-runs/gpu$g ) &
done; wait
```

Eight cards, sixteen sub-runs, **one distinct digest**:

`28f3ea04985094d46b3384064c62cd9af7bfca37e7c3467821dea3f30dc0b7b1`

Identical to the pre-resize value on this box and to the second box's. Runs are
therefore comparable across cards and across machines, and the arm-to-box split
carries no hardware confound. Driver 610.43.02 and 81920 MiB on all eight.

Note the probes ran concurrently, one per card, which is also the condition the
real suite runs under -- consistent with the co-tenancy result above.

**`--profile-kernels` cannot be used on this hardware.** It panics the Thunder
runtime (`panic(TnrDataSockMon): ... The Thunder server has crashed or become
unresponsive`) and kills the training subprocess mid-digest. Kernel profiling
goes through CUPTI, which the virtualisation layer does not implement. Nothing
in a real run touches it.

## 4. Storage is the binding constraint, not compute

At the committed checkpoint policy a single run writes **105.5 GB** (181
weights-only at 0.5 GB, 10 full at 1.5 GB). This host has 100 GB total. **One
run does not fit.** Legal alternatives, computed with the repo's own plan rule
(`full_interval` must stay an exact multiple of `weights_only_interval`):

| `weights_only_interval` | GB/run | 40 runs | 20 runs |
| --- | --- | --- | --- |
| **50 (committed)** | 105.5 | 4.22 TB | 2.11 TB |
| 100 | 58.0 | 2.32 TB | 1.16 TB |
| 200 | 34.0 | 1.36 TB | 0.68 TB |
| 500 | 20.0 | 0.80 TB | 0.40 TB |
| 1000 (full only) | 15.0 | 0.60 TB | 0.30 TB |

Reducing the interval is a measurement decision, not a housekeeping one, and is
adjacent to D-5. Nothing here rules on it.

## 5. Corpus

Rebuilt on this host from the pinned revision rather than transferred.

**Stage 1.** `scripts/corpus_fetch.py` retrieved 25 source files,
**7,572,655,845 bytes in 59 s** -- matching `docs/measurements/11-corpus.md`
exactly.

**Stage 2.** `scripts/corpus_tokenize.py` wrote 150 of 150 blocks in
**2,003 s**. `corpus_verify.py` reports `OK -- complete and consistent`:
150 blocks hashed, 149 boundaries checked, 2,510,290,944 tokens from manifest
and from disk, training tokens 2,499,805,184 as expected, held-out disjoint,
**tokenizer probe agrees**.

The tokenizer identity matches the original build to the digit --
`probe_file_sha256 b55dbe00...`, `probe_token_sha256 e47ede6a...`,
`transformers 5.14.1`, `tokenizers 0.22.2`. All ten `data_order` permutation
digests in `11-corpus.json` reproduce exactly against
`data_order.seed_digest(seed, 2441216)`.

### The manifest sha256 does NOT match, and it cannot

Rebuilt: `465ee71c945f2308b4e02548418471dbc10acfc6a9949a583b565be168c6ab10`.
Committed for the original build:
`e305bea71aa68c8ad355b7da3915125530b65a5de391f8dc08766b8b9dd5b255`.

**This is a defect in the check, not evidence of a bad corpus.**
`manifest.json` contains `elapsed_seconds_last_run` -- on this host, `2003.37`
-- and `blocks_written_last_run`, and the hash is taken over the whole file.
A wall-clock float is inside the hashed bytes, so **no rebuild on any machine
can ever reproduce the recorded manifest hash**, however byte-identical its
shards. `docs/handoff-pilot.md` §4's instruction to compare that value is sound
for a corpus that was *copied* and meaningless for one that was *rebuilt*.

**What this leaves unproven.** Nothing committed to this repo carries a
per-shard hash -- `11-corpus.json` records the manifest hash, the tokenizer
probe, and the data-order digests, none of which is a content hash of the
shards. So the structural checks above are all passing and byte-identity with
the corpus on Zach's machine is **not established**.

**How to settle it in one command.** A timing-independent content digest over
every block's recorded hash, canonically ordered:

```bash
python - <<'EOF'
import json, hashlib
m = json.load(open("<corpus>/manifest.json"))
items = sorted((b["filename"], b["sha256"]) for b in m["blocks"].values())
h = hashlib.sha256()
for fn, sha in items:
    h.update(f"{fn}:{sha}\n".encode())
print(len(items), h.hexdigest())
EOF
```

On this host: `150  c338fd06805d2f3ef18b44f3a612e19b97626977354a886b40d068a620e68ed1`.

**CONFIRMED 2026-08-08.** Asa ran the same digest against the corpus on his
machine (`corpus-tokenized/tokenized`) and it printed
`150  c338fd06805d2f3ef18b44f3a612e19b97626977354a886b40d068a620e68ed1` --
identical. All 150 block hashes agree, so the shards are byte-for-byte the same
data. **The rebuilt corpus is a drop-in for the pilot's, and runs trained here
are comparable to pilot v2.** Nothing needed transferring.

Two things follow that are worth having written down:

- **The corpus is reproducible from the pinned revision.** Fetch plus tokenize
  on a bare host takes ~35 minutes and lands on identical bytes. Provisioning a
  second training box does not require moving 5 GB across a home connection --
  rebuild in place and compare this digest.
- **The manifest hash still fails on that same corpus**, which is the cleanest
  possible demonstration that it is the check, not the data, that is wrong.
  A byte-identical corpus reports a different `manifest sha256`.
